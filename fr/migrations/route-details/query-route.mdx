# Détails de l'itinéraire

Migrer avant : T1 2027

Migrez de l'ancien service Route vers la dernière version. Le nouveau service offre un schéma réorganisé, des préférences d'opérateur par pays, un calcul d'itinéraire plus rapide et une meilleure maintenabilité.

## Opérations

| Ancien             | Nouveau                                               |
| ------------------ | ------------------------------------------------------|
| `route`            | [`getRoute`](/api-reference/light-vehicle/route/query-get-route)     |
| `routeUpdatedById`  | [`route`](/api-reference/light-vehicle/route/subscription-route)     |

## Changements généraux du schéma

- **Typage explicite** : les champs JSON auparavant flexibles sont désormais explicitement typés dans le schéma pour améliorer la structure et la validation.
- **Conventions de nommage** : les champs utilisent désormais `snake_case` au lieu de `camelCase`.
- **Prise en charge des unités** : les entrées numériques prennent désormais en charge différents types d'unités, exprimées sous la forme d'un objet avec `value`, `type` et une `source` facultative (`manual`, `telemetry` ou `default`).

## Changements de requête et de souscription

Le nommage et le regroupement des champs ont été revus, et les champs redondants ont été supprimés. La réponse inclut désormais l'entrée d'origine enrichie des valeurs par défaut, afin de pouvoir la réutiliser pour de futurs recalculs d'itinéraire.

### Niveau supérieur

Au niveau supérieur, la plupart des champs passent sous `recommended`, et les entrées `ev`, `telemetry` et `routeRequest` sont regroupées dans un seul objet `request_input`.

| Champ          | Déplacé vers           |
| -------------- | ---------------------- |
| `route`        | `recommended`          |
| `alternatives` | Supprimé               |
| `ev`           | `request_input`        |
| `telemetry`    | `request_input`        |
| `routeRequest` | `request_input`        |
| `app`          | `meta.app_id`          |
| `status`       | Inchangé               |

### Itinéraire

Au niveau de l'itinéraire, la plupart des champs passent sous `recommended` en conservant leur nom, avec quelques renommages explicites.

| Champ                 | Déplacé vers                         |
| --------------------- | ------------------------------------ |
| `rangeStart*`         | `range_at_origin`                    |
| `rangeEnd*`           | `range_at_destination`               |
| `charges`             | `recommended.charges`                |
| `distance`            | `recommended.distance`               |
| `consumption`         | `recommended.consumption`            |
| `chargeTime`          | `recommended.durations.charging`     |
| `polyline`            | `recommended.polyline`               |
| `pathPlot`            | `recommended.path_plot`              |
| `legs`                | `recommended.legs`                   |
| `tags`                | `recommended.tags`                   |
| `instructions`        | Supprimé                             |
| `amenityRanking`      | Supprimé                             |
| `stationsAlongRoute`  | `recommended.alternative_stations`   |

### Tronçons

Au niveau du tronçon, les autonomies suivent le même renommage que pour l'itinéraire, et les détails sur les occupants et la cargaison passent aux propriétés de localisation `origin` et `via` de chaque tronçon.

| Champ         | Déplacé vers                           |
| ------------- | --------------------------------------- |
| `rangeStart*` | `range_at_origin`                       |
| `rangeEnd*`   | `range_at_destination`                  |
| `steps`       | `sections`                              |
| `stationId`   | `recommended.legs.station.station_id`   |

Les tronçons gagnent également un nouveau champ `range_after_charge`.

## Changements mis en avant

La réponse introduit aussi une nouvelle forme, plus structurée, pour les sections d'itinéraire. Elle est détaillée ci-dessous.

### Sections

Les étapes (steps) ont été remplacées par des sections, qui fournissent des informations plus fines, notamment les détails d'origine et de destination de chaque section.

```graphql Sections {{ mark: [1,13,14,26,27] }}
sections {
  type
  tags
  polyline(decimals: five)
  distance(unit: meter)
  duration
  consumption
  origin {
    id
    type
    properties {
      occupants
      total_occupant_weight
      total_cargo_weight
    }
    geometry {
      type
      coordinates
    }
  }
  destination {
    id
    type
    properties {
      occupants
      total_occupant_weight
      total_cargo_weight
    }
    geometry {
      coordinates
      type
    }
  }
}
```
