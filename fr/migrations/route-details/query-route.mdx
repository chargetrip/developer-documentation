# Détails de l'itinéraire

Migrer avant : T1 2027

Migrez de l'ancien service Route vers la dernière version. Le nouveau service apporte un schéma réorganisé, des préférences d'opérateurs par pays, un calcul d'itinéraire plus rapide et une meilleure maintenabilité.

## Opérations

| Ancien             | Nouveau                                               |
| ------------------ | ------------------------------------------------------|
| `route`            | [`getRoute`](/api-reference/core/route/query-get-route)     |
| `routeUpdatedById`  | [`route`](/api-reference/core/route/subscription-route)     |

## Modifications générales du schéma

- **Typage explicite** : les champs JSON auparavant flexibles sont désormais explicitement typés dans le schéma pour améliorer la structure et la validation.
- **Conventions de nommage** : les champs utilisent désormais `snake_case` au lieu de `camelCase`.
- **Prise en charge des unités** : les entrées numériques prennent désormais en charge différents types d'unités, exprimées sous la forme d'un objet avec `value`, `type` et un `source` facultatif (`manual`, `telemetry` ou `default`).

## Modifications des requêtes et des souscriptions

Le nommage et le regroupement des champs ont été revus, et les champs redondants ont été supprimés. La réponse inclut désormais l'entrée d'origine enrichie des valeurs par défaut, afin qu'elle puisse être réutilisée pour de futurs recalculs d'itinéraire.

### Niveau supérieur

Au niveau supérieur, la plupart des champs passent sous `recommended`, et les entrées `ev`, `telemetry` et `routeRequest` sont regroupées dans un seul objet `request_input`.

| Champ          | Déplacé vers           |
| -------------- | ---------------------- |
| `route`        | `recommended`          |
| `alternatives` | Supprimé               |
| `ev`           | `request_input`        |
| `telemetry`    | `request_input`        |
| `routeRequest` | `request_input`        |
| `app`          | `meta.app_id`          |
| `status`       | Inchangé               |

### Itinéraire

Au niveau de l'itinéraire, la plupart des champs passent sous `recommended` en conservant leur nom, avec quelques renommages explicites.

| Champ                 | Déplacé vers                         |
| --------------------- | ------------------------------------ |
| `rangeStart*`         | `range_at_origin`                    |
| `rangeEnd*`           | `range_at_destination`               |
| `charges`             | `recommended.charges`                |
| `distance`            | `recommended.distance`               |
| `consumption`         | `recommended.consumption`            |
| `chargeTime`          | `recommended.durations.charging`     |
| `polyline`            | `recommended.polyline`               |
| `pathPlot`            | `recommended.path_plot`              |
| `legs`                | `recommended.legs`                   |
| `tags`                | `recommended.tags`                   |
| `instructions`        | Supprimé                             |
| `amenityRanking`      | Supprimé                             |
| `stationsAlongRoute`  | `recommended.alternative_stations`   |

### Tronçons

Au niveau des tronçons, les autonomies suivent les mêmes renommages que l'itinéraire, et les détails sur les occupants et la cargaison passent dans les propriétés de lieu `origin` et `via` de chaque tronçon.

| Champ         | Déplacé vers                           |
| ------------- | --------------------------------------- |
| `rangeStart*` | `range_at_origin`                       |
| `rangeEnd*`   | `range_at_destination`                  |
| `steps`       | `sections`                              |
| `stationId`   | `recommended.legs.station.station_id`   |

Les tronçons gagnent également un nouveau champ `range_after_charge`.

## Changements marquants

La réponse introduit également une nouvelle structure plus détaillée pour les sections d'itinéraire. Elle est décrite plus en détail ci-dessous.

### Sections

Les étapes ont été remplacées par des sections, qui fournissent des informations plus granulaires, notamment les détails d'origine et de destination de chaque section.

```graphql Sections {{ mark: [1,13,14,26,27] }}
sections {
  type
  tags
  polyline(decimals: five)
  distance(unit: meter)
  duration
  consumption
  origin {
    id
    type
    properties {
      occupants
      total_occupant_weight
      total_cargo_weight
    }
    geometry {
      type
      coordinates
    }
  }
  destination {
    id
    type
    properties {
      occupants
      total_occupant_weight
      total_cargo_weight
    }
    geometry {
      coordinates
      type
    }
  }
}
```
